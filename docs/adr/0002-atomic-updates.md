# 0002. Атомарные UPDATE вместо блокировок в Redis

Статус: принято (фаза 3).

## Контекст

В перемену много студентов одновременно заказывают последние порции и места в одном слоте.
Нельзя продать порцию или место дважды. Наивный код «прочитать остаток → проверить → записать»
ломается: два запроса читают «осталось 1» и оба записывают заказ.

Варианты:
1. Распределённая блокировка в Redis (`SET NX` / Redlock) вокруг проверки и записи.
2. `SELECT ... FOR UPDATE` строки блюда и слота.
3. Один условный `UPDATE ... WHERE остаток >= :qty RETURNING` в той же транзакции, что и заказ.

## Решение

Вариант 3 (SPEC 5.3):

```sql
UPDATE menu_items SET available_portions = available_portions - :qty
WHERE id = :id AND available_portions >= :qty RETURNING available_portions;

UPDATE pickup_slots SET booked_count = booked_count + 1
WHERE id = :id AND booked_count < capacity AND NOT is_closed RETURNING booked_count;
```

Если строка не вернулась, сервис бросает `DomainError` (`sold_out` или `slot_full`, 409), и
транзакция откатывается целиком. Ограничения `CHECK (available_portions >= 0)` и
`CHECK (booked_count <= capacity)` в базе — вторая линия защиты.

Почему не Redis:
- Остатки живут в PostgreSQL. Блокировка в Redis не входит в транзакцию базы: если процесс
  упадёт между блокировкой и commit, или блокировка истечёт по TTL раньше commit, данные
  разойдутся.
- Это ещё один отказ и ещё один сетевой запрос на каждый заказ.
- Корректность Redlock спорна, а проверить её тестами сложно.

Почему не `FOR UPDATE`: тоже корректно, но это два запроса и удержание блокировки на всё
время между ними. Условный `UPDATE` делает то же одним запросом, блокировка строки держится
минимально.

## Последствия

- Тесты с потоками: 50 параллельных заказов на 30 мест дают ровно 30 успешных, за последнюю
  порцию из двух заказов побеждает один (`backend/tests/test_orders.py`).
- Нагрузочный тест: 500 студентов, ни одного перепроданного слота или порции
  (`docs/load-test.md`).
- Отмена и автоотмена возвращают порции и места такими же атомарными `UPDATE`.
- Redis используется только там, где не нужна транзакционность: pub/sub, лимиты частоты,
  коды подтверждения.
