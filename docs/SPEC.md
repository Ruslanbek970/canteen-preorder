# Предзаказ в университетской столовой — техническое задание

Рабочее название проекта: **Canteen Pre-order**. Репозиторий: `canteen-preorder`.

Этот документ описывает весь проект от пустой папки до работающей системы на сервере. По нему работает Claude Code (правила для него лежат в `CLAUDE.md` в корне), а команда по нему проверяет, что ничего не забыто.

Связанные файлы:

- `docs/schema.sql` — эталонная схема базы (PostgreSQL), 22 таблицы, триггеры, представления, тестовые данные. Это источник правды для моделей и миграций.
- `docs/er_diagram.png` — ER-диаграмма этой схемы.
- `docs/PROGRESS.md` — журнал выполнения фаз. Claude Code обновляет его после каждой фазы.

## 1. О проекте

### 1.1 Проблема

На большой перемене в университетской столовой очередь занимает до половины перемены. Кухня готовит «на глаз»: одни блюда заканчиваются к 12:30, другие к вечеру выбрасывают. Студенты с аллергиями не знают точного состава блюд.

### 1.2 Решение

Веб-приложение (PWA), в котором:

1. Студент заранее видит меню с остатками порций, составом и аллергенами.
2. Выбирает слот выдачи. Система предлагает только слоты, которые попадают в его перемену по расписанию группы, и не даёт переполнить слот.
3. Оплачивает заказ и получает QR-код.
4. Кухня видит заказы на экране по слотам, отмечает статусы и печатает наклейку с номером.
5. На выдаче кассир сканирует QR и отдаёт заказ.
6. Система прогнозирует спрос на каждое блюдо, предлагает скидки на остатки и считает, сколько еды выбросили.

### 1.3 Роли

| Роль | Кто это | Что делает в системе |
|---|---|---|
| `student` | студент | меню, заказы, оплата, QR, история, отзывы, аллергии |
| `teacher` | преподаватель | всё как у студента, но без привязки к расписанию группы |
| `cook` | повар | экран кухни, статусы заказов, наклейки, списание остатков |
| `cashier` | кассир | выдача по QR, продажа на кассе без предзаказа |
| `canteen_manager` | заведующая столовой | меню на день, блюда и рецепты, скидки, слоты, отчёты |
| `admin` | администратор системы | пользователи и роли, столовые, корпуса, группы, импорт расписания |

### 1.4 Метрики успеха (их показываем на защите)

- среднее время ожидания в очереди до и после пилота (замер вручную);
- доля заказов через предзаказ;
- точность прогноза спроса (MAE и MAPE против базовой модели «среднее за 4 прошлые такие же дни недели»);
- количество выброшенных порций в день;
- доля незабранных заказов (no-show);
- p95 времени ответа API под нагрузкой и отсутствие переполнения слотов при одновременных заказах.

### 1.5 Что не входит в проект

- реальная интеграция с банком и онлайн-кассой: делаем интерфейс и заглушку (mock), реальный провайдер подключается позже;
- нативные мобильные приложения: вместо них PWA;
- доставка еды по кампусу.

## 2. Технологии

### Backend
- Python 3.12, FastAPI, Pydantic v2
- SQLAlchemy 2.0 (синхронный режим, драйвер psycopg 3) + Alembic
- PostgreSQL 16, Redis 7
- JWT-аутентификация (access + refresh), пароли через bcrypt
- APScheduler в отдельном процессе `worker` для фоновых задач
- aiogram 3 для Telegram-бота
- pandas + scikit-learn для прогноза спроса
- ruff (линтер и форматтер), pytest, httpx

### Frontend
- React 18+ с TypeScript, Vite
- React Router, TanStack Query (запросы к API), Zustand (корзина)
- Tailwind CSS
- i18next: языки `ru`, `kk`, `en`
- `qrcode.react` (показ QR), `html5-qrcode` (сканер QR для кассира)
- Recharts (графики в отчётах)
- vite-plugin-pwa (установка на телефон, офлайн-кэш меню)
- ESLint, Prettier, Vitest + Testing Library, Playwright (e2e)

### Инфраструктура
- Docker, Docker Compose (dev и prod)
- Nginx (раздаёт фронт, проксирует `/api` и `/ws`)
- GitHub Actions (CI и CD), образы в GitHub Container Registry
- Prometheus + Grafana (метрики), структурные JSON-логи
- k6 (нагрузочное тестирование)
- Mailpit в dev для писем

Часовой пояс системы: `Asia/Almaty` (UTC+5). В базе всё хранится в `timestamptz`, на экран выводится в локальном времени. Деньги — `NUMERIC(10,2)` в базе и `Decimal` в Python, никаких float. Суммы округляются до целых тенге.

## 3. Архитектура

```
 Студент (телефон, PWA) ─┐
 Кухня (планшет) ────────┤        ┌──────────────────────────┐
 Кассир (планшет/ПК) ────┼─HTTPS─▶│ nginx                    │
 Заведующая, админ (ПК) ─┘        │  /       → frontend      │
                                  │  /api    → backend:8000  │
                                  │  /ws     → backend:8000  │
                                  └────────────┬─────────────┘
                                               │
                        ┌──────────────────────▼───────────────┐
                        │ backend (FastAPI, uvicorn)           │
                        │  routers → services → repositories   │
                        └───────┬──────────────────┬───────────┘
                                │                  │ pub/sub (события заказов)
                         ┌──────▼──────┐     ┌─────▼─────┐
                         │ PostgreSQL  │     │  Redis    │
                         └──────▲──────┘     └─────▲─────┘
                                │                  │
                        ┌───────┴──────────────────┴───────────┐
                        │ worker (APScheduler): слоты, no-show, │
                        │ скидки, прогноз, напоминания          │
                        └───────────────────┬──────────────────┘
                                            │
                                   ┌────────▼────────┐
                                   │ telegram-bot     │
                                   └─────────────────┘
 Prometheus ← /metrics backend     Grafana ← Prometheus
```

Слои backend:
- `api/routers` — только HTTP: разбор запроса, проверка роли, вызов сервиса, ответ.
- `services` — вся бизнес-логика и транзакции.
- `repositories` (или запросы прямо в сервисах через SQLAlchemy) — доступ к данным.
- `models` — SQLAlchemy-модели, `schemas` — Pydantic-схемы запросов и ответов.

Живые обновления (экран кухни, статус заказа у студента): сервис после изменения заказа публикует событие в Redis-канал `orders:{canteen_id}`, WebSocket-эндпоинты подписаны на канал и пересылают события клиентам.

## 5. База данных

### 5.1 Источник правды

Схема описана в `docs/schema.sql`. Её нужно перенести в проект так:

1. SQLAlchemy-модели для всех 22 таблиц с теми же именами, типами, ограничениями (CHECK, UNIQUE) и внешними ключами. ENUM-типы — через `sqlalchemy.Enum(..., name="order_status", create_type=...)`, имена типов как в schema.sql.
2. Первая миграция Alembic создаёт схему. Триггеры (`set_order_timestamps`, `log_order_status`) и представления (`v_dish_allergens`, `v_menu_today`, `v_kitchen_board`) создаются в миграции через `op.execute(...)` с текстом из schema.sql.
3. Тестовые данные из раздела 6 schema.sql **не** кладутся в миграцию. Они переносятся в `scripts/seed.py`.
4. Схема PostgreSQL — `public` (не `canteen`), чтобы не писать префиксы.

### 5.2 Изменения к schema.sql (сделать отдельной второй миграцией)

| Изменение | Зачем |
|---|---|
| Таблица `daily_counters (canteen_id, service_date, prefix, last_value, PK(canteen_id, service_date, prefix))` | номера заказов A-001, A-002… без гонок |
| Таблица `refresh_tokens (id, user_id FK, token_hash, expires_at, revoked_at, created_at)` | выход из системы и отзыв сессий |
| `canteens.pickup_shelves_count SMALLINT NOT NULL DEFAULT 10` | число полок выдачи |
| `canteens.order_cutoff_minutes SMALLINT NOT NULL DEFAULT 15` | за сколько минут до начала слота закрывается заказ |
| `canteens.slug VARCHAR(50) UNIQUE` | короткая ссылка для QR у входа: `/c/main` |
| `orders.pickup_shelf SMALLINT` | номер полки, назначается при статусе `ready` |
| `users.email_verified_at TIMESTAMPTZ` | подтверждение почты |
| Таблица `push_subscriptions (id, user_id FK, endpoint, p256dh, auth, created_at)` | Web Push (фаза 8) |
| Таблица `forecast_runs (id, run_at, target_date, model, mae, mape, details JSONB)` | история прогнозов и их точности |
| Таблица `class_breaks` не нужна | перемены вычисляются из `class_schedule` |

Любое другое изменение схемы — только через новую миграцию и с записью в `docs/PROGRESS.md`.

### 5.3 Транзакции и гонки (обязательно)

Главный риск: 200 человек одновременно заказывают в один слот последние порции. Правила:

- Списание порций делается одним атомарным запросом на каждую позицию:
  `UPDATE menu_items SET available_portions = available_portions - :qty WHERE id = :id AND available_portions >= :qty RETURNING id`.
  Если строка не вернулась — откат всей транзакции и ответ `409 Conflict` с понятным текстом («Плов закончился, осталось 0 порций»).
- Бронирование слота так же:
  `UPDATE pickup_slots SET booked_count = booked_count + 1 WHERE id = :id AND booked_count < capacity RETURNING id`.
- Позиции заказа обрабатываются в порядке возрастания `menu_item_id`, чтобы не было взаимных блокировок.
- При отмене заказа порции и место в слоте возвращаются в той же транзакции.
- Кто меняет статус, передаётся в триггер через `SET LOCAL app.current_user_id = '<id>'` внутри транзакции.
- Номер заказа: `INSERT INTO daily_counters ... ON CONFLICT (...) DO UPDATE SET last_value = daily_counters.last_value + 1 RETURNING last_value`. Префикс `A` для приложения, `K` для кассы, формат `A-007`.

### 5.4 Демо-данные (`scripts/seed.py`)

- 2 корпуса, 1 столовая (`slug = main`), 3 группы с расписанием на все будние дни;
- по одному аккаунту на каждую роль и 20 студентов; пароль для всех демо-аккаунтов `demo1234`:
  `student@demo.kz`, `teacher@demo.kz`, `cook@demo.kz`, `cashier@demo.kz`, `manager@demo.kz`, `admin@demo.kz`;
- 9+ блюд с рецептами и аллергенами (как в schema.sql), меню и слоты на сегодня и завтра;
- 8 недель синтетической истории продаж (`ml/synthetic_history.py`) для обучения прогноза. В интерфейсе отчётов и в README явно пометить, что история синтетическая;
- команда `make seed` пересоздаёт демо-данные.

## 7. Бизнес-правила

### 7.1 Регистрация и вход
- Студенты и преподаватели регистрируются сами по почте из списка доменов `ALLOWED_EMAIL_DOMAINS` (например, `uni.kz,stud.uni.kz`).
- После регистрации на почту приходит 6-значный код подтверждения (в dev письма ловит Mailpit). Без подтверждения заказывать нельзя.
- Сотрудников создаёт администратор.
- Access-токен живёт 15 минут, refresh-токен 30 дней (хранится хэш в `refresh_tokens`, при обновлении старый отзывается).
- Онбординг после первого входа: группа (для студентов), язык, аллергии с отдельной галочкой согласия на хранение данных о здоровье.

### 7.2 Меню
- Студент видит меню выбранной столовой на сегодня, а после 15:00 и на завтра.
- У каждого блюда: цена, цена со скидкой (если есть активная скидка), остаток порций, КБЖУ, состав, аллергены, значки «халяль» и «вегетарианское», средняя оценка.
- Если остаток 0 — блюдо видно, но кнопка «В корзину» неактивна с текстом «Закончилось».
- Фильтры: категория, «без моих аллергенов», халяль, вегетарианское.

### 7.3 Аллергии
- Проверка по правилам, не через ИИ: аллергены блюда = объединение аллергенов его ингредиентов.
- Если у пользователя есть аллерген блюда с `severity = severe` — блюдо нельзя добавить в корзину, сервер отвечает `422` с текстом.
- Если `mild` или `moderate` — показывается предупреждение, заказ проходит только с `allergy_warning_ack = true`.
- Проверка повторяется на сервере при создании заказа, даже если клиент её уже сделал.
- Данные об аллергиях хранятся только если заполнено `health_data_consent_at`. Отзыв согласия удаляет все строки `user_allergens` пользователя.

### 7.4 Слоты выдачи
- Слоты генерирует фоновая задача каждый день в 05:00 на сегодня и завтра: от `opens_at` до `closes_at` с шагом `default_slot_minutes`, вместимость `default_slot_capacity`. Заведующая может поменять вместимость конкретного слота или закрыть его.
- Студенту показываются только слоты, которые:
  1. не пересекаются с его парами в этот день (запрос с `OVERLAPS` по `class_schedule` его группы);
  2. начинаются не раньше чем через `order_cutoff_minutes` от текущего момента;
  3. ещё не заполнены (`booked_count < capacity`).
- Преподаватели видят все доступные слоты.
- Если в слоте действует скидка `off_peak`, на нём значок «−10%».

### 7.5 Заказ
- В заказе от 1 до 10 позиций, каждой позиции от 1 до 10 штук.
- Цена позиции фиксируется в `order_items.unit_price` на момент заказа. Скидка по активной акции записывается в `discount_amount` и `promotion_id`.
- `subtotal` и `discount_total` считает сервер, клиенту не доверяем.
- Создание заказа (одна транзакция): проверить аллергии → списать порции → забронировать слот → получить номер → создать `orders` и `order_items` → создать платёж в статусе `pending` → вернуть ссылку на оплату.
- Неоплаченный заказ (`pending_payment`) старше 10 минут отменяется фоновой задачей, порции и место в слоте возвращаются.

### 7.6 Статусы заказа

```
pending_payment ──оплата──▶ paid ──повар──▶ cooking ──повар──▶ ready ──кассир──▶ picked_up
      │                      │                                  │
      └────▶ cancelled ◀─────┘                                  └──через 30 мин после конца слота──▶ no_show
```

Разрешённые переходы (всё остальное → `409`):

| Из | В | Кто |
|---|---|---|
| pending_payment | paid | система (успешная оплата) |
| pending_payment | cancelled | студент, система (таймаут) |
| paid | cancelled | студент, если до начала слота больше 30 минут; деньги возвращаются (refund в mock) |
| paid | cooking | повар (по одному или весь слот сразу) |
| cooking | ready | повар; при этом назначается полка `pickup_shelf` |
| ready | picked_up | кассир после сканирования QR |
| ready | no_show | система через 30 минут после конца слота |

При `no_show` создаётся запись в `waste_records` с `reason = uncollected_order` по каждой позиции. Если у студента 3 no-show за 30 дней, при следующем заказе показывается предупреждение (без блокировки).

### 7.7 Оплата
- Интерфейс `PaymentProvider` с методами `create_payment(order) -> PaymentIntent(url)`, `handle_webhook(payload)`, `refund(payment)`.
- `MockPaymentProvider`: ссылка ведёт на страницу фронта `/pay/mock/:paymentId` с кнопками «Оплатить» и «Отказ». Кнопка вызывает `POST /api/payments/mock/{id}/confirm|fail`, это имитирует вебхук.
- Успешная оплата → `payments.status = succeeded`, `fiscal_receipt_number` генерируется заглушкой, заказ → `paid`.
- Продажа на кассе: способ `cash` или `kaspi_qr` (выбор вручную), платёж сразу `succeeded`.
- Реальный провайдер подключается новым классом без изменения сервисов.

### 7.8 Кухня
- Экран показывает заказы на сегодня по слотам, три колонки: «Оплачены», «Готовятся», «Готовы».
- Сверху сводка по ближайшим слотам: «к 12:00 собрать: Плов × 14, Лагман × 9».
- Кнопка «Взять в работу весь слот» переводит все `paid` заказы слота в `cooking` и открывает печать наклеек.
- Наклейка 58×40 мм (печать из браузера, CSS `@page`): крупный номер заказа, время слота, позиции, строка «АЛЛЕРГИЯ: …» если есть.
- При `ready` система назначает полку (по кругу от 1 до `pickup_shelves_count`) и отправляет студенту уведомление «Заказ A-007 готов, полка 3».
- Новый заказ на экране кухни появляется без перезагрузки (WebSocket) со звуком.
- В конце дня повар нажимает «Закрыть день»: остатки `available_portions` по каждому блюду записываются в `waste_records` с `reason = expired`, если блюдо нельзя хранить до завтра (`shelf_life_hours < 24`).

### 7.9 Выдача и касса
- Кассир сканирует QR камерой планшета (или вводит номер заказа). Система показывает номер, полку, позиции, пометку об аллергии и статус.
- Выдать можно только заказ в статусе `ready`. Если заказ ещё готовится, показать это крупно.
- Экран продажи на кассе (POS): выбор блюд из меню дня, способ оплаты, кнопка «Продать». Создаёт заказ с `channel = cashier` без пользователя и слота и сразу переводит его в `picked_up`. Порции списываются так же атомарно.

### 7.10 Скидки
- `leftover`: фоновая задача каждые 30 минут после 13:30 ищет блюда, у которых остаток больше 25% от плана и до конца срока годности (`cooked_at + shelf_life_hours`) меньше 2 часов. Для таких блюд создаётся скидка 30% в статусе `proposed`. Заведующая подтверждает или отклоняет одной кнопкой. После подтверждения уходит рассылка студентам, которые заказывали это блюдо за последние 30 дней и не отключили рассылки.
- `off_peak`: заведующая вручную создаёт скидку на слот. Система подсказывает слоты, заполненные меньше чем на 30% за час до начала.
- `loyalty`: 1 балл за каждые 100 ₸ оплаченного и забранного заказа. В первой версии баллы только копятся и показываются в профиле.
- На одну позицию действует максимум одна скидка, выбирается самая большая.

### 7.11 Уведомления
- Каналы: в приложении (таблица `notifications`), Telegram (если привязан), Web Push (если разрешён).
- События: заказ оплачен; заказ готов (с полкой); напоминание за 5 минут до начала слота, если заказ ещё не забран; скидка на остатки; заказ отменён.
- Тексты на языке пользователя (`preferred_language`), шаблоны в `app/i18n`.
- Пользователь может отключить рекламные рассылки (скидки), служебные уведомления отключить нельзя.

### 7.12 Отзывы
- Оценка от 1 до 5 и комментарий доступны после `picked_up` в течение 48 часов, один раз на позицию (`dish_reviews.order_item_id` уникальный).
- Средняя оценка блюда показывается в меню, если отзывов не меньше 3.

### 7.13 Прогноз спроса
- Каждую ночь в 02:00 worker считает прогноз порций на завтра для каждого блюда в меню и пишет в `menu_items.forecast_portions` и `forecast_model`, а итог прогона в `forecast_runs`.
- Две модели:
  1. `baseline_avg` — среднее продаж этого блюда в те же дни недели за последние 4 недели;
  2. `gbm_v1` — GradientBoostingRegressor. Признаки: день недели, неделя семестра, праздник/сессия (флаг из конфига), число пар у всех групп в этот день, цена, была ли скидка, сколько блюд той же категории в меню, продажи блюда за прошлую неделю.
- Отдаётся та модель, у которой ниже MAE на последних 2 неделях (backtest).
- Заведующая видит прогноз при составлении меню и сама задаёт `planned_portions`.
- В `ml/` лежит ноутбук или скрипт `evaluate.py`, который строит таблицу и график «прогноз против факта» для диплома.

### 7.14 Время и деньги
- Все времена в `Asia/Almaty`. «Сегодня» определяется по этому поясу, а не по UTC.
- Суммы считаются в `Decimal`, на экране без копеек: `1 500 ₸`.

## 9. Экраны

11. **Профиль:** имя, группа, язык, аллергии и согласие, привязка Telegram, бонусные баллы, выход.

## 10. Фоновые задачи (worker)

| Задача | Когда | Что делает |
|---|---|---|
| `generate_slots` | каждый день 05:00 и при старте | слоты на сегодня и завтра для всех активных столовых |
| `expire_unpaid_orders` | каждую минуту | `pending_payment` старше 10 минут → `cancelled`, возврат порций и места |
| `mark_no_show` | каждые 5 минут | `ready` и прошло 30 минут после конца слота → `no_show` + списание |
| `slot_reminders` | каждую минуту | напоминание за 5 минут до начала слота |
| `propose_leftover_discounts` | каждые 30 минут с 13:30 до закрытия | правило 7.10 |
| `suggest_off_peak` | каждые 30 минут | подсказки заведующей по пустым слотам |
| `forecast_tomorrow` | каждый день 02:00 | прогноз на завтра, запись в `forecast_runs` |
| `expire_promotions` | каждые 10 минут | `valid_to` прошёл → `expired` |
| `db_backup` | каждый день 03:00 (в prod, отдельный контейнер) | `pg_dump`, хранить 14 дней |

Задачи идемпотентны: повторный запуск не создаёт дублей. Каждая задача пишет в лог начало, итог и длительность.

## 12. Безопасность

- Пароли bcrypt, минимум 8 символов. JWT подписывается `JWT_SECRET` из env.
- Проверка роли на каждом эндпоинте через зависимость `require_roles(...)`. Сотрудник получает данные только своей столовой.
- Ограничение частоты запросов (Redis): вход — 5 попыток в минуту с IP, создание заказа — 10 в минуту на пользователя.
- CORS только для домена фронта. HTTPS в prod (Let's Encrypt через nginx или Caddy).
- Все входные данные валидируются Pydantic. SQL только через ORM или параметризованные запросы.
- Секреты только в `.env`, в репозитории `.env.example` без значений.
- Данные о здоровье: доступ только владельцу, согласие обязательно, отзыв удаляет данные. В README раздел о том, что по закону РК персональные данные хранятся на серверах в Казахстане.
- Заголовки безопасности в nginx (CSP, X-Frame-Options, HSTS в prod).

## 13. Тестирование

### Backend (pytest, отдельная тестовая БД в Docker)
- Модели и миграции: `alembic upgrade head` и `downgrade base` проходят на чистой базе.
- Сервисы (обязательные кейсы):
  - заказ списывает порции и бронирует слот; последняя порция уходит только одному из двух параллельных заказов (тест с потоками);
  - слот не переполняется при 50 параллельных заказах на 30 мест;
  - аллергия `severe` блокирует, `mild` требует подтверждения;
  - все запрещённые переходы статусов дают ошибку;
  - отмена возвращает порции и место;
  - `expire_unpaid_orders` и `mark_no_show` работают и идемпотентны;
  - номер заказа уникален в пределах дня при параллельных заказах;
  - расчёт скидок и итоговой суммы;
  - фильтр слотов по расписанию.
- API: каждый эндпоинт хотя бы один успешный кейс и проверка прав (чужая роль получает 403).
- Покрытие backend не ниже 70%.

### Frontend
- Vitest: корзина (сумма, скидки), фильтры меню, форматирование цены и времени.
- Playwright e2e (на поднятом docker compose с демо-данными):
  1. студент входит, заказывает, оплачивает, видит QR;
  2. повар переводит заказ в «готов»;
  3. кассир находит заказ по номеру и выдаёт;
  4. студент видит статус «выдан».

### Нагрузка (k6, `infra/k6/order_rush.js`)
- 500 виртуальных студентов за 5 минут создают заказы в 6 слотов по 30 мест и на ограниченные порции.
- Цели: p95 < 500 мс, ошибок 5xx нет, `booked_count <= capacity` у всех слотов, `available_portions >= 0` у всех блюд. После теста скрипт проверяет это SQL-запросом.
- Результат (графики k6 и Grafana) сохраняется в `docs/load-test.md` для диплома.

### 14.6 CI (`.github/workflows/ci.yml`, на каждый push и PR)
1. backend: ruff check, ruff format --check, pytest с сервисами postgres и redis, отчёт о покрытии;
2. frontend: npm ci, eslint, tsc --noEmit, vitest, vite build;
3. сборка Docker-образов (без публикации на PR);
4. e2e Playwright — на push в `main` и вручную.

### 14.7 CD (`.github/workflows/deploy.yml`, на push в `main` после зелёного CI)
1. собрать и опубликовать образы в GHCR с тегами `sha` и `latest`;
2. по SSH на сервер: `docker compose -f docker-compose.prod.yml pull && up -d`;
3. `alembic upgrade head` отдельной командой перед переключением;
4. проверить `/api/v1/health/ready`, при ошибке откатиться на предыдущий тег.

Секреты GitHub: `SSH_HOST`, `SSH_USER`, `SSH_KEY`, `GHCR_TOKEN` (или `GITHUB_TOKEN`), `PROD_ENV` (содержимое `.env`).

### 14.8 Мониторинг и логи
- `prometheus-fastapi-instrumentator` на backend, свои метрики: `orders_created_total`, `orders_by_status`, `slot_fill_ratio`, `job_duration_seconds`, `job_failures_total`.
- Grafana с готовым дашбордом (provisioning): RPS, p95 латентность, ошибки 5xx, заказы в минуту, заполненность слотов, работа фоновых задач.
- Алерты: 5xx > 2% за 5 минут, БД недоступна, задача падает 3 раза подряд.
- Логи JSON (structlog) с `request_id` в каждом запросе.

### 14.9 Бэкапы
Ежедневный `pg_dump` в том `backups`, хранение 14 дней, инструкция восстановления в `docs/deployment.md`. Восстановление один раз проверить и описать.

### 14.10 Бонус (если останется время)
Манифесты Kubernetes или Helm-чарт в `infra/k8s/` (Deployment, Service, Ingress, HPA для backend), локальная проверка в kind или minikube.

## 17. Сценарий демонстрации на защите (5–7 минут)

1. Проблема одним слайдом: очередь и выброшенная еда.
2. Телефон студента: меню, у блюда с орехами красная пометка (у демо-студента аллергия), выбор слота — показываются только перемены.
3. Оплата, на экране QR и статус «Оплачен».
4. Планшет кухни: заказ появился сам, «Взять слот в работу», печать наклейки, «Готов» — у студента сразу приходит «Полка 3».
5. Касса: сканирование QR, «Выдать».
6. Панель заведующей: прогноз против факта, предложенная скидка на остатки, отчёт по списаниям.
7. Grafana во время k6-теста: 500 заказов за 5 минут, слоты не переполнились.
8. Результаты пилота (если был): время в очереди до и после.
