## Решения

Сюда записываются решения, принятые по ходу работы, если в ТЗ чего-то не хватало.

- Фаза 0. `/health/ready` (SPEC 8.10) добавлен сразу вместе с `/health`: он нужен для healthcheck и CD, а проверка БД и Redis — это одна функция.
- Фаза 0. React 18 + React Router 6 (флаги v7 включены), Tailwind 3.4 с `darkMode: 'media'` (тёмная тема по системной настройке, SPEC 9). Node 22 в Docker и CI.
- Фаза 0. Пакеты backend ставятся через `pip install -e ".[dev]"` из `backend/pyproject.toml`, без отдельного менеджера зависимостей.
- Фаза 0. Dev-фронт в Docker проксирует `/api` и `/ws` на `backend:8000` через Vite (`VITE_API_PROXY_TARGET`), поэтому в браузере всё идёт с `localhost:5173`.
- Фаза 0. Защита страниц по ролям (guard-ы) появится в фазе 1 вместе со входом; сейчас страницы по ролям открыты и пустые, на главной есть ссылки на все разделы.
- Фаза 0. `make e2e` и `make load-test` пока печатают сообщение: Playwright и k6 появятся в фазе 11.
- Фаза 1. Миграция 1 создаёт 22 таблицы, индексы, триггеры и представления из schema.sql (SQL триггеров и представлений вписан в миграцию дословно, кроме префикса схемы). Миграция 2 — изменения из SPEC 5.2.
- Фаза 1. В миграцию 2 добавлено поле `users.marketing_opt_out` (по умолчанию `false`): SPEC 8.1 говорит, что в `PATCH /me` меняется «согласие на рассылки», а в schema.sql для него нет поля.
- Фаза 1. Группа студента выбирается при регистрации, а не в онбординге: в schema.sql есть CHECK `role <> 'student' OR group_id IS NOT NULL`, поэтому студента без группы создать нельзя. В онбординге группу можно поменять.
- Фаза 1. Код подтверждения почты хранится в Redis (хэш, 30 минут, 5 попыток). Добавлен `POST /auth/resend-code`, иначе с просроченным кодом подтвердить почту нельзя.
- Фаза 1. Лимит входа «5 попыток в минуту с IP» считает только неудачные попытки: в университете много людей выходят в интернет с одного IP.
- Фаза 1. Без подтверждённой почты можно войти и смотреть меню, но нельзя заказывать (проверка появится в фазе 3).
- Фаза 1. Онбординг показывается один раз на устройстве (флаг в localStorage), его можно пропустить.
- Фаза 1. Тесты backend работают с отдельной базой `<имя>_test` (создаётся сама) и Redis db 15, перед каждым тестом таблицы очищаются. Так `make test` не трогает демо-данные.
- Фаза 1. В dev контейнер backend при старте сам применяет миграции и, если база пустая, загружает демо-данные (`AUTO_SEED=true`). Поэтому после `git pull` достаточно `docker compose up -d --build`.
- Фаза 1. Фронт в Docker сам переустанавливает npm-пакеты, если после `git pull` изменился `package-lock.json` (иначе том `node_modules` остаётся старым).
- Фаза 2. Меню на завтра студент видит после 15:00 по Алматы; запрос другой даты даёт 422 `menu_date_unavailable`. Средняя оценка показывается при 3+ отзывах.
- Фаза 2. `PUT /manager/menu` заменяет меню дня: новые блюда добавляются, изменённые обновляются, убранные удаляются, если по ним ещё нет заказов (иначе 409). При изменении плана уже заказанные порции сохраняются: остаток = план − заказано.
- Фаза 2. Добавлен `GET /dish-categories` (нужен форме блюда) и `GET /manager/dishes/{id}`.
- Фаза 2. Фильтры меню (категория, «без моих аллергенов», халяль, вегетарианское) работают на клиенте по уже загруженному меню дня.
- Фаза 3. Чтобы заведующая могла «закрыть слот» (SPEC 7.4), миграция 3 добавила `pickup_slots.is_closed`. Закрытый слот не показывается и не бронируется.
- Фаза 3. Добавлен `POST /manager/slots/generate?date=`: на случай, если фоновая задача не создала слоты. Пока worker нет (фаза 4), слоты на сегодня и завтра создаются при старте backend.
- Фаза 3. Платёж создаётся вместе с заказом в статусе `pending`, но `payment_url` пока `null`: ссылку на mock-оплату даёт провайдер из фазы 4. Способ оплаты в приложении по умолчанию `kaspi_qr`.
- Фаза 3. Заказ из приложения получает канал `mobile_app` и префикс номера `A`. День заказа — день слота. Заказать можно только на день, меню которого сейчас открыто (сегодня, после 15:00 и завтра).
- Фаза 3. Скидка в строке считается за штуку с округлением до тенге, потом умножается на количество, чтобы итог совпадал с ценой «со скидкой» в меню. На строку одна скидка — наибольшая из `leftover` и `off_peak`.
- Фаза 3. Чужой заказ отвечает 404, а не 403, чтобы не раскрывать, что такой заказ есть.
- Фаза 3. Для заказа нужна подтверждённая почта (403 `email_not_verified`). Лимит 10 заказов в минуту на пользователя.
- Фаза 3. «Повторить» собирает корзину на открытый день: пропускает блюда, которых нет в меню, закончились или опасны для пользователя, и говорит, что пропущено.
- Фаза 3. Корзина хранится в браузере (Zustand + localStorage), одна корзина на одну столовую и один день.
- Фаза 3. В dev, если в базе уже есть данные, при старте последнее меню копируется на сегодня и завтра, если на эти дни меню нет. Так демо не пустеет на следующий день.
- Фаза 4. Публичный `POST /payments/webhook/mock` закрыт (404): mock «вебхук» — это только `confirm`/`fail` от владельца заказа, иначе любой мог бы оплатить чужой заказ. Эндпоинт вебхука остаётся для настоящего провайдера.
- Фаза 4. После «Отказ» заказ остаётся `pending_payment`; добавлен `POST /orders/{id}/pay`, он даёт новую ссылку на оплату (или прежнюю, если она ещё открыта). Если оплата пришла после автоотмены, платёж сразу помечается `refunded`.
- Фаза 4. События для WebSocket копятся в сессии БД и уходят в Redis pub/sub только после commit; при откате не уходят. Канал `/ws/kitchen/{id}` сделан сразу (для фазы 5), туда не попадают данные об аллергиях.
- Фаза 4. Worker — отдельный сервис `worker` в docker-compose (APScheduler). Он ждёт, пока backend применит миграции. Сейчас в нём `generate_slots` (05:00 и при старте) и `expire_unpaid_orders` (каждую минуту); остальные задачи добавляются в своих фазах.
- Фаза 4. QR-код содержит только `qr_token` заказа (UUID), рисуется на клиенте библиотекой `qrcode`.
- Фаза 5. Полка назначается по кругу через тот же атомарный счётчик `daily_counters` (префикс `S`), поэтому две готовые одновременно порции не получат одну полку случайно.
- Фаза 5. «Закрыть день» списывает остатки блюд со сроком хранения меньше 24 часов и обнуляет их остаток; блюда со сроком 24 часа и больше остаются на завтра. Повторное нажатие ничего не списывает. Ручное списание: причины «испорчено», «срок годности», «другое»; «заказ не забрали» ставит только система.
- Фаза 5. Уведомление студенту «Заказ готов, полка N» пока приходит как обновление статуса через WebSocket (на странице заказа появляется полка); push и Telegram — фаза 8.
- Фаза 5. Доска: касание кнопки на карточке переводит заказ дальше; все детали (позиции, аллергия, полка) уже на карточке, поэтому отдельного «долгого касания» нет. Звук включается кнопкой (браузеры не дают играть звук без действия пользователя).
- Фаза 5. Строка «АЛЛЕРГИЯ: …» на кухне и на наклейке всегда на русском (как в SPEC), независимо от языка интерфейса.
- Фаза 6. Продажа на кассе сразу создаётся заказом в статусе `picked_up` (канал `cashier`, без пользователя и слота, номер с префиксом `K`) и успешным платежом с фискальным номером mock; это единственное место, где заказ создаётся не в `pending_payment`, поэтому таблица переходов для неё не используется.
- Фаза 6. Номер на кассе можно ввести коротко: `7`, `a7`, `A-7` → `A-007`; `k3` → `K-003`. Поиск по номеру только среди заказов сегодняшнего дня своей столовой; заказ другой столовой отвечает 404.
- Фаза 6. Сканер QR — камера браузера (`getUserMedia`) и библиотека `jsQR`; если камеры нет, номер вводится вручную.
- Фаза 6. Для e2e отдельный скрипт `scripts/e2e_setup.py` создаёт столовую «Тестовая столовая (e2e)», открытую круглые сутки, и пользователей `e2e-*@demo.kz` (заказчик — преподаватель, чтобы не зависеть от перемен). E2E в CI запускается только на push в `main` и вручную.
- Фаза 7. Синтетическая история (`backend/ml/synthetic_history.py`) создаётся при `make seed` и при старте dev-контейнера: прошлые будни за 8 недель, у которых ещё нет заказов. В ней есть закономерности для прогноза (день недели, плов по четвергам, рост доли предзаказа с 42 до 62 %, пики в перемены) и шум. Заказы делают неактивные аккаунты `customerNNN@synthetic.demo` (войти под ними нельзя), у демо-аккаунтов своя небольшая история без опасных для них блюд. Граница синтетики хранится в `canteens.synthetic_history_until` (миграция 0004), отчёты и дашборд показывают «Данные до … синтетические».
- Фаза 7. Продажами считаются оплаченные заказы (`paid`…`picked_up` и `no_show`: незабранный заказ оплачен, потом списан). Выручка = сумма `orders.total`. Доля no-show считается только среди предзаказов, которые уже закончились (выдан или не забран). Списания относятся к дню меню (`menu_items.menu_date`).
- Фаза 7. Период отчётов по умолчанию 28 дней (оценки — 56), не длиннее 366 дней. CSV в UTF-8 с BOM, чтобы Excel открыл кириллицу: продажи — по дням и блюдам, списания — каждая запись, пиковые слоты и оценки — как в таблице на экране. Отчёт «прогноз против факта» появится в фазе 9.
- Фаза 7. Оценку ставят на странице заказа (кнопка «Оценить» в «Моих заказах»): 1–5 звёзд и комментарий, один раз на позицию, только после выдачи и не позже 48 часов. Средняя оценка в меню показывается от 3 отзывов (сделано в фазе 2).
- Фаза 7. Страница отчётов с графиками (Recharts) загружается отдельным файлом только для заведующей и админа, чтобы студенту не скачивать библиотеку графиков.
- Фаза 8. Каждое уведомление — строка в `notifications` с каналом `in_app` (миграция 0005 добавила значение в enum и колонку `kind`); Telegram и Web Push — способы доставки той же строки, отдельных строк для них нет. Уникальный индекс `(order_id, kind)` не даёт прислать одно и то же уведомление о заказе дважды (повтор задачи, гонка двух worker).
- Фаза 8. Отправка в Telegram и Web Push не блокирует запрос: после коммита сообщение кладётся в очередь Redis (`outbox:telegram` читает бот, `outbox:push` — worker каждые 15 секунд). При откате транзакции ничего не уходит. Неудачная отправка пишется в лог и не повторяется; подписка браузера, которая ответила 404/410, удаляется.
- Фаза 8. Уведомления в приложении приходят живыми по тому же `/ws/me` (событие `notification.new`), колокольчик в шапке показывает число непрочитанных.
- Фаза 8. Скидку на остатки (30 %) система предлагает с 13:30 каждые 30 минут, если осталось больше 25 % плана и блюдо испортится в ближайшие 2 часа (`cooked_at + shelf_life_hours`); действует до порчи или до закрытия столовой. На одну позицию меню — одно предложение, отклонение окончательное. После одобрения уведомление получают покупатели блюда за 30 дней, кроме отключивших рекламу.
- Фаза 8. Скидку на непиковый слот (20 %) система тоже только предлагает (слот начинается в течение часа и занят меньше чем на 30 %), а заведующая может сама сразу создать скидку на любой будущий слот сегодня (5–50 %). Студентам о слотовых скидках отдельно не пишем: их видно при выборе слота.
- Фаза 8. Баллы лояльности начисляются при выдаче заказа: 1 балл за каждые 100 ₸ суммы. Тратить баллы в ТЗ не описано, поэтому пока только копим и показываем в профиле.
- Фаза 8. Напоминание приходит за 5 минут до начала слота оплаченного и ещё не выданного заказа.
- Фаза 8. Привязка Telegram: в профиле кнопка выдаёт одноразовый 6-значный код на 10 минут (хранится в Redis), его отправляют боту `/start 123456` или открывают ссылку `t.me/<бот>?start=…`. Один чат — один аккаунт. Команды бота: `/orders`, `/stop`. Без `TELEGRAM_BOT_TOKEN` контейнер `bot` просто ждёт, остальная система работает.
- Фаза 8. Web Push работает, только если в `.env` заданы ключи VAPID (`python -m scripts.generate_vapid_keys`); иначе в профиле написано, что push не настроен. Отдельный service worker `frontend/public/push-sw.js`, в фазе 11 его объединим с PWA.
- Фаза 8. В `test_scheduler_has_jobs` добавлены новые задачи worker: тест проверяет точный список задач, а он вырос по ТЗ.
- Фаза 9. Спрос = проданные порции позиции меню (заказы `paid`…`picked_up` и `no_show`, вместе с кассой). Он упирается в план (продать больше, чем приготовили, нельзя), это ограничение данных, записанное как есть.
- Фаза 9. `gbm_v1` использует признаки из SPEC 7.13 и ещё номер блюда (без него модель не отличает плов от чая). Параметры подобраны на демо-данных: 400 деревьев глубины 2, функция потерь — абсолютная ошибка (метрика выбора тоже MAE). «Продажи за прошлую неделю» = среднее за 7 предыдущих дней. «Была ли скидка» для будущего дня всегда 0: скидки решаются в сам день.
- Фаза 9. Модель выбирается заново при каждом прогоне: обучаем на всём до последних 14 дней, проверяем на этих 14 днях, в меню идёт модель с меньшей MAE. Если истории меньше 50 позиций, работает только `baseline_avg`.
- Фаза 9. Ночная задача `forecast_tomorrow` в 02:00 считает не только завтра, а все дни с уже составленным меню от сегодня до +7 дней, чтобы заведующая видела прогноз, когда составляет меню заранее. Прогноз пишется в `menu_items.forecast_portions/forecast_model`, прогон — в `forecast_runs`; в `details` лежат столовая, результаты backtest и предсказания обеих моделей по каждой позиции (отчёт сравнивает модели по ним).
- Фаза 9. Чтобы отчёт «прогноз против факта» был не пустой сразу после запуска, при `make seed` и старте dev-контейнера прогоны «задним числом» считаются за последние 14 дней (каждый день — только на данных до него, `details.backfill = true`).
- Фаза 9. Модели (scikit-learn, pandas) загружаются только в worker и скриптах; API считает MAE/MAPE простым кодом (`ml/metrics.py`). MAPE не учитывает позиции, где продали 0.
- Фаза 10. Импорт расписания заменяет целиком расписание каждой группы, которая есть в файле; группы, которых в файле нет, не трогаем. Если в файле есть хоть одна ошибка, ничего не сохраняется: админ видит все ошибки по строкам, исправляет файл и загружает снова. Сначала «Проверить» (`dry_run=true`), потом «Импортировать». Разделитель — запятая или точка с запятой (Excel в русской локали сохраняет с `;`), кодировка UTF-8 (с BOM или без), первая строка-заголовок необязательна. Группы и корпуса в файле должны уже существовать (корпус ищется по названию без учёта регистра), новые из файла не создаются.
- Фаза 10. Корпуса и группы по SPEC 8.9 только создаются и просматриваются (`GET/POST`), редактирования и удаления нет. Столовую не удаляем, а выключаем (`is_active`): у неё есть история заказов.
- Фаза 10. Пользователь, созданный админом, сразу считается с подтверждённой почтой. Столовая сохраняется только у сотрудников (повар, кассир, заведующая), группа — только у студента; при смене роли лишнее очищается. Блокировка, новый пароль или новая роль отзывают все refresh-токены пользователя. Себя админ заблокировать или лишить роли админа не может.
- Фаза 10. В списке пользователей нет данных об аллергиях и согласии на них: их видит только сам пользователь (SPEC 6).
- Фаза 11. PWA сделана своим service worker (`public/sw.js`) без vite-plugin-pwa: он один и для офлайн-кэша, и для Web Push из фазы 8 (прежний `push-sw.js` переименован в `sw.js`). Кэшируются оболочка приложения, файлы сборки и только «справочные» ответы API: список столовых, меню дня и карточка блюда (сначала сеть, без сети — последний ответ). Заказы, QR и профиль не кэшируются. Меню содержит отметки об аллергенах конкретного пользователя, поэтому при выходе этот кэш удаляется. Без сети кнопка заказа выключена, сверху баннер «Нет сети». Service worker регистрируется только в продакшен-сборке, в `npm run dev` его нет.
- Фаза 11. Зелёный `green-600` с белым текстом даёт контраст 3,3:1 (меньше 4,5:1 по WCAG AA), поэтому кнопки и активные вкладки стали `green-700`. Видимый фокус с клавиатуры добавлен глобально (`:focus-visible`). Доступность проверяется в e2e через axe (WCAG 2.1 A/AA) на экранах студента при ширине 360 px, кухни и кассы.
- Фаза 11. Экраны персонала (кухня, касса, заведующая, админка) грузятся отдельными чанками (`React.lazy`): основной бандл для студента уменьшился с 679 до 486 КБ.
- Фаза 11. Нагрузочный тест нашёл зависание: пул потоков FastAPI (40) больше пула соединений (30), и под давкой запросы ждали 30 с. Пул соединений вынесен в `DB_POOL_SIZE`/`DB_MAX_OVERFLOW` (10 + 10), пул потоков ограничен тем же числом. Подробности в `docs/load-test.md`.
- Фаза 11. Нагрузочный тест идёт на отдельной столовой `load-*` и пользователях `load-NNN@load.demo`, данные создаёт `scripts/load_setup.py`. k6 в docker compose запускается только с профилем `load` (`make load-test`).

Остальные предупреждения — в инструментах разработки (vitest, tailwind), в сборку не попадают.
- Фаза 12. Бизнес-метрики (`orders_created_total`, `orders_by_status`, `slot_fill_ratio`) считает worker запросом к базе при каждом опросе Prometheus, а не счётчики в процессах API: так числа не зависят от того, какой процесс gunicorn принял заказ, и не сбрасываются при перезапуске. Добавлены `canteen_db_up` (для алерта «БД недоступна») и `job_consecutive_failures` (для алерта «задача упала 3 раза подряд»).
